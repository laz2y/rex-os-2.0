# REX OS 3.0 — Deployment Guide

Deploying REX OS 3.0 to your NAS alongside the existing REX OS 1.0 / 2.x
installations. **Nothing in this guide overwrites older REX OS installs.**

---

## 1. What the production build is

The production build is the Vite build of the frontend: **`dist/`**
(generated by `bun run build` → `tsc -b && vite build`).

`server.js` finds that build in **either** layout, checked in this order, so
both the dev checkout and the packaged REX Updater release work unchanged:

1. `<backend>/dist` — packaged runtime, where the release nests the UI inside
   the backend directory
2. `<backend>/../dist` — development checkout (Vite writes to the repo root),
   or any deploy that keeps `dist/` next to `backend/`

A directory counts only when it contains `index.html`. If neither exists the
server still boots as a pure JSON API (`GET /` returns API info).

It includes:

- The full REX OS 3.0 UI (all pages, glass theme system, auth flow)
  - Dashboard, Pipeline, Diagnostics, Activity, Notifications
  - System Monitor, Docker Manager, Storage Dashboard
  - Media Center (Jellyfin + Radarr/Sonarr), Downloads (qBittorrent + pyLoad),
    Photos (Immich), Global Search
  - Cloud, Direct Link, Settings
  - Updates, Backups, Recovery
- The six uploaded wallpaper assets:
  - `dist/assets/goku.png`
  - `dist/assets/luffy.png`
  - `dist/assets/naruto.png`
  - `dist/assets/all_three.png`
  - `dist/assets/background.png`
  - `dist/assets/banner.png`
- No credentials — all service tokens/passwords/JWT secret stay
  server-side in `backend/.env` / `backend/.auth-secrets.json`.

## 2. Files to copy to your NAS

Copy **both** the frontend build and the backend into a fresh directory
on the NAS (e.g. `/opt/rexos-3.0/`):

```
dist/                     ← the Vite production build (entire folder)
backend/                  ← the Express API (entire folder)
  ├── server.js
  ├── package.json
  ├── routes/
  ├── controllers/
  ├── services/
  ├── smoke.js
  └── data/               ← state (activity, notifications, pipeline,
                            recovery, update, backups) — mount as a
                            persistent volume so state survives restarts
```

**REX OS 3.0 development release:** `backend/.auth-secrets.json` ships in
this archive with the existing test/development credentials so the release
can be deployed and tested immediately. Before the final production
deployment, replace those values with your real credentials (the backend
reads `backend/.env` first, then `backend/.auth-secrets.json`).

Then, on the NAS, from inside `backend/`:

```
npm install --omit=dev     # installs express, axios, bcryptjs, jwt, etc.
```

## 3. Start command

From the NAS, inside the new deploy directory:

```
cd /opt/rexos-3.0/backend
PORT=4000 node server.js
```

That starts one process on **port 4000** that serves BOTH:

- the REX OS UI (`dist/` — served statically with SPA fallback), and
- the `/api` backend (health, auth, system, docker, jellyfin, nextcloud,
  immich, pyLoad, qBittorrent, radarr, sonarr, search, pipeline,
  diagnostics, activity, notifications, storage, terminal, updates,
  backups, recovery).

Recommended: run it under a process manager or systemd so it survives
reboots. Example systemd unit:

```
[Unit]
Description=REX OS 3.0
After=network.target

[Service]
WorkingDirectory=/opt/rexos-3.0/backend
ExecStart=/usr/bin/node server.js
Environment=PORT=4000
Environment=COOKIE_SECURE=true
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

## 4. Required environment variables

All server-side, all in `backend/.env` (or exported in the process env).
**Use your existing NAS credentials — do not generate new ones.**

| Variable | Purpose |
|---|---|
| `PORT` | API/UI port (default 4000) |
| `COOKIE_SECURE` | `true` behind HTTPS so the auth cookie is TLS-only |
| `REX_USERNAME` | Login username (`admin`) |
| `REX_PASSWORD_HASH` | bcrypt hash of the login password (never plaintext) |
| `JWT_SECRET` | Long random string signing session JWTs |
| `PORTAINER_URL` | e.g. `https://portainer.laz2ynas.cc` |
| `PORTAINER_API_TOKEN` | Portainer access token |
| `PORTAINER_ENDPOINT_ID` | Docker endpoint id (3) |
| `JELLYFIN_URL` | e.g. `https://jellyfin.laz2ynas.cc` |
| `JELLYFIN_API_KEY` | Jellyfin API key |
| `NEXTCLOUD_URL` | e.g. `https://cloud.laz2ynas.cc` |
| `NEXTCLOUD_USERNAME` | Nextcloud admin user |
| `NEXTCLOUD_PASSWORD` | Nextcloud app password |
| `IMMICH_URL` | e.g. `https://immich.laz2ynas.cc` |
| `IMMICH_API_KEY` | Immich API key |
| `QBITTORRENT_URL` | e.g. `https://qb.laz2ynas.cc` |
| `QBITTORRENT_USERNAME` | qBittorrent user |
| `QBITTORRENT_PASSWORD` | qBittorrent app password |
| `PYLOAD_URL` | pyLoad web/API base. Container deployment (recommended): `http://pyload:8000` (Docker service name — see §4a below). Non-Docker / reverse-proxy: e.g. `https://pyload.laz2ynas.cc` |
| `PYLOAD_USERNAME` | pyLoad login user |
| `PYLOAD_PASSWORD` | pyLoad login password |
| `RADARR_URL` | Radarr base, e.g. `https://radarr.laz2ynas.cc` |
| `RADARR_API_KEY` | Radarr API key |
| `SONARR_URL` | Sonarr base, e.g. `https://sonarr.laz2ynas.cc` |
| `SONARR_API_KEY` | Sonarr API key |

Optional tunables (all have safe defaults):

| Variable | Default | Purpose |
|---|---|---|
| `REX_MONITOR_MS` | `60000` | Auto-recovery probe interval |
| `REX_RECOVERY_MAX_ATTEMPTS` | `3` | Restart attempts per failure window |
| `REX_RECOVERY_COOLDOWN_MS` | `600000` | Cooldown before retrying a failed service |
| `REX_STORAGE_WARN` / `REX_STORAGE_CRIT` | `70` / `85` | Storage thresholds (%) |
| `REX_BACKUP_INTERVAL` | `86400000` | Automatic backup interval (ms, min 1h) |
| `REX_DISABLE_BACKUPS` | — | `true` disables the automatic backup scheduler |
| `REX_UPDATE_MAX_UPLOAD` | `536870912` | Update package upload cap (bytes) |

Optional override file: `backend/.auth-secrets.json` — fill-gap values
for the same keys, plus `REX_PASSWORD_HASH` which always overrides.

### 4a. Docker networking — pyLoad ↔ rex-backend (permanent fix)

When `rex-backend` runs as a container (the REX Updater deployment), it must
reach pyLoad **by Docker service name** (`http://pyload:8000`), never by IP
address. Docker's embedded DNS only resolves names of containers attached to
the **same** network as the caller. The classic failure: `rex-backend` is on
`rex-net` while `pyload` is only on `rexos`, so `getent hosts pyload` fails
inside rex-backend and Direct Link Add errors out (the API returns a clear
"hostname did not resolve — Docker network?" message in REX OS 2.5+).

The permanent fix is a **compose-file change** (survives reboot, `docker
compose up`, Watchtower recreation and REX Updater rollback — `docker network
connect` alone does NOT, it is lost on container recreation). The change is
exactly two things: `pyload` declares **both** networks, and the shared
`rex-net` is declared as an external network. Everything else about pyLoad is
untouched.

**Option A — drop-in override (recommended).** The repository ships the
exact fragment at `deploy/pyload-rex-net.override.yml`. Copy it next to the
NAS stack's base compose as the auto-loaded override file, then recreate
pyload:

```bash
cd <stack-dir-on-nas>
cp docker-compose.yml docker-compose.yml.bak-$(date +%F)   # back up first
cp /path/to/rexos/deploy/pyload-rex-net.override.yml docker-compose.override.yml
# if docker-compose.override.yml already exists, merge the two blocks into it
# instead of overwriting it
docker compose up -d pyload          # recreates pyload with both networks
```

**Option B — merge inline into the base compose** (same result, no extra
file):

```yaml
services:
  pyload:
    # ...existing config...
    networks:
      - rexos        # keep the existing network — do not remove it
      - rex-net      # NEW: lets rex-backend resolve 'pyload'

networks:
  rexos:            # keep the existing declaration as-is
    external: true
  rex-net:          # add this if the stack does not already declare it
    external: true
```

Then ensure the backend points at the Docker service name:

```bash
docker inspect rex-backend --format '{{range .Config.Env}}{{println .}}{{end}}' | grep PYLOAD_URL
# must read:  PYLOAD_URL=http://pyload:8000
# if it points elsewhere, update the rex-backend env and recreate it through
# the normal REX Updater update path so the env applies
```

Verify from inside rex-backend (no IPs anywhere):

```bash
docker exec rex-backend getent hosts pyload
# → should print an IP (e.g. 172.x.x.x) — previously "bad address"

docker exec rex-backend wget -qO- --timeout=10 http://pyload:8000/api/info
# → should return pyLoad's JSON API info instead of "bad address"
```

Finally test Direct Link Add in REX OS with a real direct-download URL, and
confirm a manual add through pyLoad's own UI still works. `rexos` stays
intact, so pyLoad's existing connectivity to the rest of the arr stack is
unaffected.

## 5. State, backups, updates and rollback

- **State** lives in `backend/data/` (JSON files, atomic writes). Mount it
  as a persistent volume — state survives container recreation.
- **Backups** are created automatically once per day (and on demand from
  the Backups page) into `backend/data/backups/`. They contain REX OS state
  only — never media libraries, never secrets (`backend/.env` and
  `.auth-secrets.json` are excluded).
- **Updates** follow a safe pipeline: upload → validate (archive safety,
  manifest, semver, disk space) → create a rollback point → install
  (stage + syntax-check + verify). The running API cannot restart its own
  container — after an install, recreate the REX container from the staged
  release to activate it (see `rex-updater/DESIGN.md`).
- **Rollback** restores the pre-update REX state from the last rollback
  point (Recovery page / Updates page).

## 6. Rollback to REX OS 1.0

Because 3.0 lives in its own directory (`/opt/rexos-3.0/`), rollback is
just a service switch:

1. Stop the 3.0 service: `sudo systemctl stop rexos3`
2. Start the existing 1.0 / 2.x service: `sudo systemctl start rexos1`
   (or whatever your older process manager was — a simple process swap)
3. Verify the older version is serving on its port and `/api/health`
   responds.

Your older REX OS files were never touched — the 3.0 install is fully
independent, so rollback is instant and lossless.

## 7. Verification checklist (after starting 3.0)

```
curl http://localhost:4000/api/health        # → 200 {"status":"ok","version":"2.5.0",...}
curl http://localhost:4000/                  # → the REX OS UI (index.html)
curl http://localhost:4000/api/auth/me       # → 401 when logged out
curl http://localhost:4000/assets/goku.png   # → 200 (each of the 6 assets)
curl http://localhost:4000/api/system/connections   # → services status
curl http://localhost:4000/api/pipeline      # → pipeline state + services
curl http://localhost:4000/api/radarr/overview      # → Radarr overview
curl http://localhost:4000/api/sonarr/overview      # → Sonarr overview
curl http://localhost:4000/api/search?q=test        # → global search
```

Session-protected endpoints (`/api/storage`, `/api/system/metrics`,
`/api/terminal/*`, `/api/update/*`, `/api/backups`, Docker stats/inspect)
return **401** without a valid `rexos_token` cookie — that is expected.
